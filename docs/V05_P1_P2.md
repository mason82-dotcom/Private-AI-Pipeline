# Light Console v0.5 — P1 abgeschlossen, P2-Umsetzung begonnen

**Stand:** 2026-10-25. Die in diesem Paket enthaltenen Quellcodedateien sind in einer isolierten Entwicklungsumgebung mit Fake-Ollama und HTTP-Tests geprüft. **Kein Nachweis für echte Docker-/Pi-/LAN-Hardware**, keine echten Nutzerprojekte importiert. Der Projektstand ist nicht automatisch nach GitHub übertragen.

## 1. P1: Funktionsumfang und Exit-Gate

| Funktion | Implementierung | Verifikation |
|---|---|---|
| Gateway getrennt vom Modellserver prüfen | `GET /api/status` | HTTP-Test gegen echten Gateway mit Fake-Ollama |
| Modellstatus `ok`, `no_models`, `unreachable`, `not_checked` | HTTP API + Light Console | Integrationstest; Upstream-Ausfall simuliert |
| Datenquelle, Zeitpunkt, Latenz je Check | `checks.gateway`, `checks.inference` | ISO-8601-Zeit + Millisekunden in HTTP-Tests |
| Modellliste ohne API-Token im Browser | `GET /api/models` | Auth- und Secret-Tests |
| Streaming mit Abbruch, keine Cloud-Ausweichroute | `POST /api/chat` (SSE) | HTTP-Streaming gegen Fake-Ollama; JS-Syntax geprüft |
| Verständlicher lokaler Fehler-/Leerzustand | Light Console | Quellcode/JS-Syntax; Browser-E2E durch Umgebung blockiert |
| Realer Raspberry Pi + Ollama | Noch nicht abgenommen | Muss auf dem Zielgerät erfolgen |

P1 ist **implementierungsseitig abgeschlossen**, aber **nicht für produktiven Betrieb freigegeben**, bevor der Betreiber die Hardware-/Netzwerkabnahme durchgeführt hat.

**Beispiel `GET /api/status` nach Anmeldung** (nur beispielhafte Struktur, keine echten Messwerte):

```json
{
  "console":"ok", "gateway":"ok", "inference":"ok",
  "source":"gateway_health", "observed_at":"2026-10-25T09:00:00+00:00",
  "checks":{
    "gateway":{"state":"ok","source":"gateway /health","observed_at":"2026-10-25T09:00:00+00:00","latency_ms":5},
    "inference":{"state":"ok","source":"gateway /v1/models","observed_at":"2026-10-25T09:00:00+00:00","latency_ms":20}
  }
}
```

**Wichtig:** Modellliste erfolgreich abgerufen ≠ Modell antwortet mit nützlichem Text ≠ garantiert kein WAN-Egress. Erst ein tatsächlicher Chat-Stream prüft Textgenerierung; WAN-Isolation benötigt einen unabhängigen Host-/Netzwerktest.

## 2. P2: tatsächlich neu implementierte Funktionen

- Unterschiedliche Tabs für **Dokumente** und **Erinnerungen** mit echten serverseitigen Daten statt erfundener Listen.
- Authentifiziertes `GET /api/knowledge?kind=documents|memory|search&q=...` an der Console; Projekt-/Namensraum ist vom Gateway **fest konfiguriert** und kann nicht aus dem Browser überschrieben werden.
- Gateway `GET /private/knowledge` und `POST /private/knowledge` mit separatem `KNOWLEDGE_TOKEN`; `PIPELINE_TOKEN` allein ist nicht ausreichend.
- Nur explizit freigeschalteter Import (`KNOWLEDGE_IMPORT_ENABLED=true` auf beiden Diensten): `.txt`, `.md`, `.rst`, max. 48 KiB Text, keine Unterpfade, keine Byte-Uploads und keine Ausführung; Dubletten nach SHA-256 pro Namespace.
- Neue SQLite-Tabelle `knowledge_documents`, weiterhin FTS5-Textabschnitte in `entries_v2`; beim erneuten Import mit gleichem Inhalt keine Duplikate. Additive Schemaänderung; ursprüngliche v0.1/v0.2-Tabellen werden nicht gelöscht.
- Kontextabhängige Quellensuche, explizite Leer-/Fehlerzustände, HTML-escaping in der UI, kein automatisches Erfassen von Chatverläufen als Memories.
- Memory-Anzeige ist **read-only**. Es gibt keine neuen Bearbeiten-/Löschen-Endpunkte.

**P2 noch offen:** PDF-/Office-Parser; semantische Embeddings, zitierfähige Quellspans für alle importierten Formate; robuste Limits pro Gesamtarchiv; Import von Ordnern mit nachvollziehbaren Versionsänderungen; Multiuser-Rechte und Projektwechsel; Chat-RAG-Integration; serverseitig auditiertes Editieren/Löschen von Erinnerungen. Keine dieser Funktionen wird vom Dashboard als produktiv dargestellt.

## 3. Architektur und Berechtigungsgrenzen

```text
Browser --(Passwortsitzung, CSRF, Same-Origin)--> Light Console (BFF)
  |                                                    |
  | keine Tokens                                      |-- PIPELINE_TOKEN -> Gateway /v1/**
  |                                                    |-- KNOWLEDGE_TOKEN -> Gateway /private/knowledge
  |                                                                          |
  |                                                                          --> SQLite knowledge_documents & entries_v2
  +-- Keine direkte Verbindung zur Gateway- oder SQLite-Adresse
```

Der Zugang ist eine **Einzelbetreiber-Konfiguration**. `KNOWLEDGE_NAMESPACE` bestimmt den einen sichtbaren Namensraum, z. B. `personal`. Nicht für ein gemeinsames LAN-Team oder mehrere private Accounts freigeben: Open WebUI und Light Console teilen **keine** User-ACLs, und die neue API enthält keine Multi-Tenant-Rollenprüfung.

## 4. Migration von P0 / v0.4 ohne vorhandene Daten zu verlieren

1. **Stoppen, Sicherung und unabhängigen Restore-Test durchführen**, bevor die Images neu gebaut werden. Vorhandene `memory_data`, `webui_data` und `.env` nicht löschen.
2. Projektdateien aus dem neuen Paket über die alte Arbeitskopie übernehmen. Bestehende `.env` belassen.
3. `bash scripts/upgrade_env_p2.sh` ergänzt fehlende Variablen, generiert nur bei Bedarf einen **neuen separaten** Knowledge-Schlüssel und setzt Dateirechte `0600`.
4. `.env` prüfen: `KNOWLEDGE_NAMESPACE=personal`, `KNOWLEDGE_IMPORT_ENABLED=false` belassen, sofern nur gelesen werden soll.
5. `bash scripts/preflight.sh` und `python3 -m unittest discover -s tests -v` ausführen.
6. Erst danach den isolierten Stack starten: `docker compose -f compose.yaml -f compose.console.yaml --profile console up -d --build`.
7. Nur lokal oder über **bereits abgesichertes** Tailscale HTTPS zugreifen: `http://127.0.0.1:38881` ist die Loopback-Bindung. Niemals ungeprüft Ports auf `0.0.0.0` öffnen.
8. Nach Authentifizierung die Tabs **Wissen & Gedächtnis** öffnen. Import erfordert bewusst `KNOWLEDGE_IMPORT_ENABLED=true` und Neustart der beiden betroffenen Dienste. Danach Import wieder deaktivieren, wenn nicht benötigt.
9. Mit Testdaten verifizieren: Datei importieren, Fundstelle suchen, zweite identische Datei importieren (Dublettenmeldung); Memory-Suche in einem anderen konfigurieren Namespace darf keine Treffer liefern.

**Bestehende Installationen:** Wenn ein neuer Schlüssel in `.env` eingetragen wird, müssen Gateway und Console dieselbe Umgebungsvariable erhalten. `scripts/init.sh` ändert absichtlich keine bestehende `.env`.

## 5. Betriebs- und Sicherheitshinweise

- Auch im lokalen Netz HTTPS nutzen, falls Zugriff über andere Geräte erforderlich wird. Bei lokalem HTTP bleibt `CONSOLE_SECURE_COOKIE=false`, bei ausschließlich HTTPS über Reverse Proxy auf `true` setzen; Vertrauensgrenzen und Proxy-Header gesondert prüfen.
- Docker `internal:true` ist eine Barriere für den standardmäßigen isolierten Compose-Betrieb, **kein** Beweis für End-to-End-Abschottung aller Profile oder des Windows-Modellhosts. Host-Firewall und tatsächliche Egress-Pakete separat prüfen.
- Die API führt hochgeladene Texte nie aus. Das schützt nicht vor **Prompt Injection im Inhalt**. Daher keine automatische Agentenausführung auf Basis von Dokumenttext; ein späterer RAG-Kontext muss als untrusted markiert werden.
- UTF-8-Import ist ein kontrollierter Texteingang, keine Malware-Bereinigung, PDF-Sanitization oder Dateisystem-Scanner.
- Keine hochgeladenen Texte, Auth-Tokens und Passwörter werden in Standard-HTTP-Logs ausgegeben. Sicherungen mit `.env` und SQLite enthalten trotzdem sensible Daten und benötigen Zugriffsschutz/Verschlüsselung.
- P1/P2-Status ist standardmäßig ausschließlich über Login und Same-Origin sichtbar. Der `/health`-Endpunkt dient nur der Service-Erreichbarkeit, nicht als Autorisierungsbeweis.
- Vor Deployment alle Image-Tags durch geprüfte Digests ersetzen, Restore-Test dokumentieren, Pi-Portkonflikte prüfen und Dienste wie SkyHub-Next, Forgejo oder Hermes-Agent unverändert lassen.

## 7. Prüfkommandos

```bash
python3 -m compileall -q gateway console tests
python3 -m unittest discover -s tests -v
node --check console/static/app.js
for f in scripts/*.sh; do bash -n "$f"; done
```

Echte Docker-/Pi-/Browser-Tests sind keine Teilmenge dieser Unit-/HTTP-Suite. In der aktuellen Ausführungsumgebung wurde der direkte Headless-Browserzugriff auf lokale HTTP-Adressen durch eine Administratorrichtlinie blockiert. Das ist kein Beweis für korrektes UI-Verhalten in einem echten Chrome/Android-Browser.
